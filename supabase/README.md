# Supabase 연결 (본편 퀘스트의 서버 부분)

1. Supabase 에서 새 프로젝트를 만든다.
2. **SQL Editor** 에 `supabase/schema.sql` 을 통째로 붙여 넣고 실행한다.
3. **Project Settings › Data API** 의 `Project URL`, **Project Settings › API Keys** 의 `Publishable key`(`sb_publishable_…`)를 복사한다.
   (예전 프로젝트라면 Legacy API Keys 탭의 `anon` 키 `eyJ…` 도 된다. `secret` 키 · `service_role` 키는 절대 넣지 않는다.)
   - GitHub 로 배포할 때: 저장소 **Settings › Secrets and variables › Actions › Variables** 에
     `SUPABASE_URL`, `SUPABASE_KEY` 두 개를 만든다. 다음 배포부터 자동으로 `config.js` 에 들어간다.
   - 직접 넣을 때: `config.js` 의 `supabaseUrl` · `supabaseAnonKey` 를 채운다.
4. 사이트를 새로 고친다. 산문 › 산문 너머 › **세계** 탭의 안내가 "서버에 모인 모든 학생의 선택"으로 바뀌면 연결된 것이다.

| 표 · 보기 | 쓰임 |
|---|---|
| `story_choices` | 본편의 주요 선택(B1-1 … B15-2). 한 사람당 분기마다 한 줄 |
| `story_tally` (보기) | 분기별 선택 집계 → 세계 탭 "세계 결정" |
| `story_contrib` · `story_contrib_totals` | 공동 사건 기여(쌍응수 · 지워진 지도 · 신격 레이드 · 오방 결전) |
| `story_progress` | 끝낸 장면 수 |
| `cloud_saves` | 기록 백업(`BiryeongSync.saveCloud` · `loadCloud` — 화면 단추는 아직 없다) |

지금 연결하면 되는 것은 **선택 집계 · 기여 올리기 · 진행도**까지다. 아래는 표만 준비되어 있고 게임 규칙에는 아직 반영하지 않았다.

- 서버 집계로 세계 값(W_)과 엔딩을 정하는 것 — 지금 엔딩은 각자의 브라우저 값으로 정한다.
- 레이드를 여럿이 동시에 치르는 것 — 지금은 각자 싸우고 기여만 올린다.
- 계정 로그인을 Supabase Auth 로 옮기는 것 — 지금 로그인은 브라우저에만 있고, 서버에서는 무작위 `player_id` 로 구분한다. 그래서 `schema.sql` 의 권한은 공개 키로 읽고 쓰게 열려 있다(지우기만 막음). 정식 로그인을 붙일 때 정책을 `auth.uid() = player_id` 로 좁힌다.


## v1.8 — 본편 장 공개 · 선택 열람

1. `schema.sql` 을 다시 통째로 실행한다(다시 실행해도 안전하다). `story_chapters` 표와 관리자 함수가 생기고, 선택지 범위가 1~12로 넓어진다.
2. 관리자 코드를 서버에 한 번 넣는다. SQL Editor 에서 '여기에 관리자 코드' 를 실제 코드로 바꿔 실행:
   ```sql
   insert into biryeong_private.admin_secret (id, code_hash) values (1, encode(sha256(convert_to('여기에 관리자 코드', 'UTF8')), 'hex'))
     on conflict (id) do update set code_hash = excluded.code_hash;
   ```
3. 사이트에서 관리자 › 스토리 관리 → 관리자 코드를 한 번 넣고 [코드 기억] → 장마다 [파일 올리기](`story-chapters/chN.json`) → [지금 공개] 또는 [이 시각에 공개].
4. 공개 전 장은 서버가 학생에게 내주지 않는다(행 수준 보안: `open_at <= now()` 인 줄만 읽힌다). 선택은 `story_choices` 에 계정 이름과 함께 모이고, 스토리 관리 아래쪽에 선택지별 인원 · 투표자가 보인다.


## v1.9 — 계정 · 기록 · 소통 공간 · 관리자

`schema.sql` 을 다시 통째로 실행하면 끝이다(다시 실행해도 안전하다). 따로 켤 설정은 없다 — Supabase Auth · Storage · Realtime 은 쓰지 않는다.

| 무엇 | 어떻게 |
|---|---|
| 계정 | 로그인 화면 그대로. 아이디 · 비밀번호(bcrypt 해시)가 서버에 저장되고, 어느 기기에서든 같은 아이디로 들어온다. 서버 연결 전에 만든 계정은 같은 비밀번호로 한 번 더 로그인하면 서버로 올라간다. |
| 기록 | 20초마다 · 화면을 떠날 때 · 로그아웃할 때 서버에 올린다. 다른 기기에서 로그인하면 서버의 기록을 받는다. |
| 낮새들의 터(타임라인) · 밤쥐들의 터(밀담) | 게임 계정 그대로 쓴다. 글은 쓴 사람과 관리자가 지울 수 있다. (vB.01 부터 지신성 · 메모 게시판은 없다) 밀담은 당사자와 관리자만 본다(관리자 열람은 감사 기록에 남는다). |
| 급식실 익명 사연 | 생활관 › 기숙사 › 급식실의 「익명 사연 투고함」. 투고하면 검토 없이 바로 「그날의 교내 신문」에 #1, #2 … 로 실린다. 쓴 사람은 화면 어디에도(관리자에게도) 나오지 않고, 쓴 본인과 관리자가 뗄 수 있다. 300자 · 한 계정 하루 30건까지. |
| 공지사항 게시판 | 첫 화면 왼쪽 [공지사항] 탭. 관리자만 쓰고 지운다(서버가 역할을 확인한다). 최신이 맨 위. 위쪽 속보 띠 공지(서버 관리)와는 따로다. |
| 본편 파티 전투 | 본편 전투 앞에서 [파티 모집하기]. 같은 장면 · 같은 전투에 와 있는 학생에게만 보이고, 3명까지 모인다(빈 자리는 연호수 · 윤진서). 판은 방장의 브라우저가 돌리므로 방장은 끝날 때까지 창을 닫지 않는다. 15분 동안 움직임이 없는 파티는 저절로 닫힌다. |
| 투표 루트 공개 | 관리자 › 스토리 관리 › 선택 집계에서 「투표」 선택 아래 [이 루트로 지금 공개] · [이 시각에 공개] · [루트 닫기]. 공개 전에는 학생들이 갈림길 뒤 장면에서 기다리고, 공개되면 모두 그 루트로 이어진다(각자 고른 것은 집계로 남는다). |
| 관리자 되기 | 로그인 화면의 '비령' 글자를 다섯 번 눌러 **관리자 코드**(위 v1.8 의 2번에서 서버에 넣은 코드)를 함께 적고 로그인한다. 그 계정이 서버에서 관리자가 된다. 이후에는 [서버 관리]에서 다른 계정을 관리자로 지정할 수 있다. |
| 관리자 › 서버 관리 | 공지(첫 화면 속보 띠) · 하사(냥 · 영력 · 아이템, 한 사람 또는 모두) · 회원(접속 현황 · 칭호 · 글쓰기 정지 · 계정 정지 · 비밀번호 초기화 · 기록 열람 · 삭제) · 감사 기록 |
| 스토리 관리 | 관리자 계정으로 로그인해 있으면 관리자 코드를 다시 묻지 않는다. |

표는 모두 `biryeong_private` 스키마에 있어 공개 키로는 직접 읽거나 쓸 수 없고, `bry_*` 함수로만 드나든다. 함수마다 로그인 때 받은 표(token)를 확인하고, 관리자 함수는 계정의 역할을 서버에서 확인한다.
Table Editor 에서 보려면 왼쪽 위 schema 를 `public` 에서 `biryeong_private` 로 바꾼다.

GitHub 의 `ADMIN_CODE` 는 서버가 없을 때만 쓰는 임시 방편이다. Supabase 를 연결하면 관리자 여부는 서버(`admin_secret` 에 넣은 코드)가 정한다.


## D.06.6 보안 패치 필수 사항

- **기존 DB**: Supabase SQL Editor에서 `supabase/security_patch_D.06.6.sql` **1회 실행**. 신규 DB는 전체 `supabase/schema.sql`을 실행하면 패치까지 포함됩니다. **ZIP만 서버에 올려서는 기존 Supabase 정책이 바뀌지 않습니다.**
- 기존 공개 `story_choices`/`story_contrib`/`story_progress`/`cloud_saves` 권한이 닫힙니다. 새 사이트는 `bry_story_choice`, `bry_story_contrib`, `bry_story_progress` RPC를 사용합니다. 이전 화면 코드와 혼용하면 직접 저장이 실패할 수 있으므로 HTML/JS를 함께 배포해야 합니다.
- 투표 원본(계정/선택/식별자)은 관리자 코드 검증을 거친 `story_admin_choices` RPC로만 조회됩니다. 일반 이용자는 집계(view)만 볼 수 있습니다.
- SQL Editor에 설정하는 관리자 코드는 **서로 다른 서비스에 재사용하지 않는 24자 이상의 무작위 문자열**을 권장합니다. 관리자 코드 검증 함수의 조회 요청량 제한이 어려운 만큼 별도 프록시/WAF도 권장합니다.
- 마켓/선물과 게임 진행 기록은 일부 클라이언트 생성 값에 의존합니다. 서버가 소지품·냥·전투 결과를 독립 검증하는 구조로 바꾸기 전까지는 **게임 재화의 부정 생성/조작을 완전히 막을 수 없습니다**.
- 이 SQL 파일은 기존 데이터를 지우지 않지만, 운영 DB는 적용 전 백업해야 합니다.
